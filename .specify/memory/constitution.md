# Minewalker Constitution

## Core Principles

### I. 探索・推理・領域拡張の一体性

Minewalkerは、周囲8マスの数字から危険を推理するマインスイーパーと、
キャラクターを直接操作する見下ろし型ダンジョン探索を一体のゲームループとして
提供しなければならない（MUST）。プレイヤーは歩行し、安全な壁を破壊して自分の
陣地と探索範囲を広げ、壁やモンスターから素材・アイテムを回収し、成長してより深い
エリアへ進めなければならない（MUST）。数字を読むだけ、戦闘するだけ、または盤面を
クリックして開くだけの実装に中核体験を分断してはならない（MUST NOT）。

理由: 推理、移動、採掘、戦闘、回収、成長の連鎖こそが本作固有の価値である。

### II. 公平な危険情報と回収可能な損失

地雷の数字は実際の周囲8マスの危険数と常に一致し、開始地点周辺は安全でなければ
ならない（MUST）。地雷生成と数字計算は、固定seedで再現可能な純粋ロジックとして
検証できなければならない（MUST）。危険マス、冷却、解除の意味を曖昧にしてはならない
（MUST NOT）。

モンスターの攻撃でHPが0になった場合、プレイヤーは自分の陣地で復活し、その時点で
所持していたアイテム、武器、防具は死亡地点に回収可能な落とし物として残らなければ
ならない（MUST）。落とし物が失われる条件と期限は仕様とUIで明示し、予告なく消去しては
ならない（MUST NOT）。

理由: 推理可能性と損失回収の見通しが、緊張感を理不尽さに変えないためである。

### III. 環境適応UIとPWA品質

UIはスマートフォン縦画面を基準にしつつ、実行環境の画面寸法、safe-area、入力方式に
応じて操作可能なレイアウトへ適応しなければならない（MUST）。主要操作のタップ領域は
44px以上、重要情報の文字は12px以上とし、HUDや操作バーでゲームワールドを操作不能に
してはならない（MUST NOT）。キーボード、ポインター、タッチのうち対象環境で利用可能な
入力に対応し、重要情報を画像内テキストだけに依存させてはならない（MUST）。

本番ビルドはインストール可能なPWAとして構成し、初回ロード後のオフライン起動、
更新通知、主要画面の実機相当サイズ表示を検証しなければならない（MUST）。

理由: 端末差によって推理や操作の成否が変わらないことが、ゲームとしての公平性に直結する。

### IV. セーブデータの安全性と互換性

永続セーブと探索中断セーブは分離し、各データはversionを持ち、ロード時に構造と値を
検証しなければならない（MUST）。破損時はバックアップを試し、既存の正常な進行を
黙って初期化してはならない（MUST NOT）。セーブ形式を変更する場合は移行関数と移行の
ユニットテストを追加し、互換性を壊す変更には明示的な移行計画が必要である（MUST）。

探索終了、強化、装備変更、設定変更、および死亡時の落とし物生成は、対応する状態変更と
矛盾しない単位で保存されなければならない（MUST）。

理由: 長期的な探索と拠点成長は、進行データを信頼できて初めて成立する。

### V. テスト必須・型安全・日本語ドキュメント

機能開発では、その振る舞いを検証するユニットテストを実装と同じ変更に含め、すべての
関連テストが成功することを完了条件としなければならない（MUST）。不具合修正には再現
テスト、ユーザージャーニーや画面遷移の変更には必要な統合テストまたはE2Eテストを
追加しなければならない（MUST）。テストを追加できない場合は、理由、代替検証、解消条件を
計画とタスクに記録し、例外承認を得なければならない（MUST）。

TypeScriptはstrictを維持し、明示的な`any`を原則禁止し、ドメイン型とreadonlyを優先する
（MUST）。新規または変更するクラス、インターフェース、フィールド、メソッド、公開関数には
日本語のドキュメントコメントを記載しなければならない（MUST）。TypeScriptではTSDoc/JSDoc
形式、XMLドキュメントコメント対応言語ではXML形式を使用する。意図が自明でない分岐、
アルゴリズム、制約には日本語のコードコメントを付ける（MUST）。

理由: 自動検証、型、読み手向けの意図説明を同時に保つことで変更時の事故を防ぐ。

## ゲームおよび技術上の制約

- ゲームタイトル「Minewalker」、見下ろし型探索、マインスイーパー要素、冷却・解除、
  拠点成長、縦画面優先方針を通常の機能変更で変更してはならない（MUST NOT）。
- マインスイーパーの数字は周囲8方向を対象とし、0は省略可能、1は青、2は緑、3は赤、
  4は紫で表示する（MUST）。
- 探索ロジックはSceneへ集中させず、盤面、移動、採掘、地雷処理、戦闘、ドロップ、
  インベントリ、カメラ、セーブの責務を分離する（MUST）。
- Vite、TypeScript、Phaser 3、Vitest、Playwright、vite-plugin-pwaを既定技術とし、
  置換には移行理由、互換性、検証方法を計画へ記載する（MUST）。
- アセットは`ART_ASSET_SPEC.md`に従い、生成モック画像をゲーム背景として使用せず、
  重要情報を画像だけで表現しない（MUST）。
- プレイヤー向け説明、開発報告、AIエージェントからユーザーへの回答は日本語とする
  （MUST）。AIエージェントの内部推論言語は成果物へ露出させない。

## 開発ワークフローと品質ゲート

1. 仕様は、中核ループへの影響、死亡と落とし物、端末別UI、セーブ互換性、測定可能な
   受け入れ条件を明示する（MUST）。
2. 計画は、責務分離、対象ユニットテスト、必要なE2E、PWA検証、日本語ドキュメント
   コメントの更新範囲を示す（MUST）。
3. タスクはテストを任意扱いせず、各機能の実装前または同一作業単位にユニットテストを
   含める（MUST）。
4. 実装は小さな単位で進め、各単位でテストを実行する。主要フロー変更時は
   `npm run lint`、`npm run test`、`npm run build`、該当する`npm run e2e`を成功させる
   （MUST）。
5. リリース完了には、主要画面の実機相当サイズ、PWAインストール、オフライン起動、
   セーブ再読込、死亡後の落とし物回収、進行不能の有無を確認する（MUST）。

## Governance

本憲章は、Minewalkerの仕様、計画、タスク、実装、レビューにおける他の慣行より優先する。
矛盾を発見した場合は、下位成果物を本憲章へ合わせなければならない（MUST）。

改正には、変更理由、影響する原則と成果物、移行または互換性への影響、検証方法を記載し、
プロジェクト所有者の承認を得なければならない（MUST）。中核ルールの削除または意味変更は
MAJOR、新原則または実質的な義務の追加はMINOR、意味を変えない明確化はPATCHとして
セマンティックバージョニングを適用する。

すべての仕様レビューとコードレビューは、5原則への適合と品質ゲートの証拠を確認する
（MUST）。例外は対象、理由、期限、解消条件を記録した場合に限り一時的に認められ、
恒久的な例外には憲章改正が必要である。

実行時の詳細規約は`AGENTS.md`、ゲーム要件は`PLAN.md`、実装手順は`SKILL.md`、
アセット要件は`ART_ASSET_SPEC.md`を参照する。
